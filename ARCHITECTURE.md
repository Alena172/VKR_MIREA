# Архитектура

## Обзор системы

Система представляет собой платформу для изучения английского языка русскоязычными пользователями через реальный контекст, короткие упражнения и интервальные повторения.

Репозиторий включает:

- серверную часть на FastAPI, построенную как модульный монолит
- клиентское приложение на React для словаря, тренировки, повторения и истории
- браузерное расширение для захвата слов с веб-страниц
- Docker Compose-конфигурацию для локального запуска всех компонентов

Текущий продуктовый цикл выглядит так:

1. Захватить или ввести слово
2. Получить перевод и определение, соответствующее контексту
3. Сохранить слово в личный словарь
4. Потренироваться на сохраненной лексике
5. Повторить слабые слова и слова, срок повторения которых уже наступил, через SRS

## Архитектура в одном взгляде

```text
Браузерное расширение ----\
                        \
Клиентское приложение ----> серверная часть FastAPI ----> PostgreSQL
                        /           |            Redis
Другие API-клиенты ----/            |
                                     +--> рабочий процесс Celery / Flower
                                     |
                                     +--> фасад AI-провайдера
```

## Основные части серверной части

Доменные модули:

- `identity`
  - `auth`: выпуск и проверка JWT
  - `users`: профиль пользователя и уровень CEFR
- `vocabulary`
  - сохраненные леммы, переводы и контекстные определения
  - внутренний сценарий `from-capture`
  - подмодули `translation` и `base_lexicon`
- `learning`
  - `exercise_engine`: генерация упражнений и фоновые задачи генерации
  - `session`: отправка ответов, проверка корректности, обратная связь
  - `review`: SRS, очередь повторения, план повторения, сводка прогресса
- `learning_graph`: семантический профиль пользователя, интересы, `WordSense`, смысловые связи

Технические адаптеры и инфраструктура:

- `ai_services`: централизованный адаптер к AI-провайдерам, локальным резервным сценариям и генерации текста
- `infrastructure/tasks`: получение статуса фоновых задач

Для модулей верхнего уровня используется единая HTTP-точка входа `api/router.py`. Крупные модули (`identity`, `learning`, `vocabulary`) дополнительно делятся на подмодули, а компактные модули (`learning_graph`, `ai_services`) сохраняют плоскую внутреннюю структуру.

## Важные архитектурные решения

### 1. Модульный монолит

Серверная часть построена как единое FastAPI-приложение в формате модульного монолита.

Модульный монолит в проекте означает:

- серверная часть разворачивается как одно приложение
- все модули используют одну базу данных и общую среду выполнения
- каждый доменный модуль владеет своей бизнес-логикой и таблицами
- межмодульные вызовы проходят через `public_api.py` и DTO из `contracts.py`

Границы модулей поддерживаются через:

- `public_api.py` для межмодульного доступа
- `contracts.py` для DTO
- `assembler.py` для преобразования `model -> DTO`
- проверку границ модулей в `backend/tools/check_module_boundaries.py`

Прямые импорты чужих `repository`, `models` или `application_service` считаются архитектурным нарушением.

### 2. AI вынесен в слой адаптера

Все AI-сценарии проходят через `app.modules.ai_services`. В архитектурной модели это технический адаптер, а не отдельный домен продукта.

Платформа использует гибридный подход к языковым операциям:

- локальные эвристики и `base_lexicon` обрабатывают простые случаи перевода
- внешний AI подключается там, где действительно нужна семантическая неоднозначность или генерация контента
- для перевода и генерации упражнений существуют резервные сценарии

Для `context_definition` словарь использует стратегию: сначала переиспользовать готовое определение, затем при необходимости обратиться к LLM.

- сначала система пытается переиспользовать уже существующее определение для той же леммы
- при отсутствии надежного кандидата вызывается AI
- вместе с определением сохраняются метаданные об источнике, уверенности и переиспользовании

### 3. Основной сценарий повторения построен вокруг SRS

Главный сценарий выбора слов связан с повторением уже известных слов, которые нужно повторять сейчас.

`learning/review` строит план повторения из:

- недавних ошибок
- слов, срок повторения которых наступил
- состояния `word_progress`

Именно этот поток сейчас наиболее важен для продукта.

### 4. Learning graph отвечает за интересы и смыслы

`learning_graph` формирует персональный семантический профиль пользователя: накапливает интересы по сохраненным словам и связывает словарные элементы с конкретными смыслами.

Он отвечает за:

- автоматическое определение интересов по сохраненным словам и их контекстам
- хранение разных смыслов одной леммы через `WordSense`
- связь словарной записи с конкретным смыслом
- простые смысловые связи: полисемия или слова из той же темы

При этом SRS остается владельцем вопроса "когда повторять", а learning graph отвечает на вопросы "какая тема пользователю ближе" и "какой смысл слова сейчас используется".

## Runtime-компоненты

### Серверная часть

- FastAPI-приложение в `backend/app/main.py`
- SQLAlchemy ORM и Alembic-миграции
- синхронная модель работы с сессией БД
- настройка CORS и доверенных хостов через параметры приложения

### База данных

- PostgreSQL - основное постоянное хранилище
- таблицы организованы по модулям серверной части
- Alembic-миграции находятся в `backend/alembic/versions`

### Фоновые задачи

- рабочий процесс Celery выполняет тяжелые операции
- Redis используется как брокер сообщений и хранилище результатов
- Flower дает мониторинг рабочего процесса Celery
- для отдельных сценариев разработки существует локальный резервный режим

### Клиентское приложение

- React + Vite + Tailwind
- состояние аутентификации хранится в хранилище браузера
- основные экраны: главная, словарь, тренировка, повторение, история

### Браузерное расширение

- браузерное расширение на Manifest V3
- читает выделенный текст с активной страницы
- вызывает `/translate/me` и `/vocabulary/me/from-capture`

## Ключевые пользовательские потоки

### Захват слова в словарь

1. Пользователь выделяет текст в браузере
2. Расширение отправляет выделение и исходное предложение
3. Серверная часть через `vocabulary/translation` переводит лемму
4. Серверная часть получает определение, соответствующее контексту
5. Элемент словаря создается или переиспользуется
6. Инициализируется SRS-прогресс
7. Синхронизируются семантические данные для learning graph

### Тренировка

1. Клиентское приложение запрашивает генерацию упражнений
2. Серверная часть ставит задачу в очередь
3. Клиентское приложение запрашивает статус `/tasks/{task_id}` через инфраструктурный API задач
4. Сгенерированные упражнения показываются в UI
5. Пользователь отправляет ответы
6. Серверная часть проверяет ответы и сохраняет сессию

### Повторение

1. Клиентское приложение загружает сводку и план повторения
2. Серверная часть строит очередь из слов к повторению сейчас и в ближайшее время
3. Оценка повторения поднимает приоритет известных слабых слов
4. Пользователь проходит SRS или случайную сессию повторения
5. После каждого ответа обновляется прогресс слова
