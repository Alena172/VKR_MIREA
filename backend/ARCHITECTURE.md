# Архитектура серверной части

## Обзор

Серверная часть представляет собой модульный монолит на FastAPI. Бизнес-логика разделена на шесть доменных модулей с явными границами. Такой подход позволяет разворачивать проект как одно приложение и удерживать доменную логику в управляемом виде.

Основные компоненты среды выполнения:

- FastAPI-приложение
- PostgreSQL
- Redis как брокер сообщений и хранилище результатов
- Celery для фоновых задач
- Flower для мониторинга задач

Серверная часть является источником истины для:

- аутентификации и пользовательской учётной записи
- словарных элементов и их контекстных определений
- контекстного перевода
- генерации и проверки упражнений
- состояния SRS-повторения и прогресса слов
- семантического профиля пользователя: интересов, смыслов слов и семантических связей

## Общая структура

Точка входа — `app/`. Бизнес-логика организована по верхнеуровневым модулям:

- `identity` — вход, регистрация, выпуск JWT, профиль пользователя и уровень CEFR
- `vocabulary` — общий словарь (`dictionary_entries`), личный словарь (`user_vocabulary`), перевод, захват слова из контекста, базовый лексикон
- `training` — генерация упражнений, учебные сессии, проверка ответов, история
- `review` — SRS-повторение, очередь повторения, план, сводка прогресса, `word_progress`
- `graph` — семантический профиль пользователя, интересы, `WordSense`, смысловые связи
- `ai` — централизованный адаптер к внешнему AI и локальным резервным сценариям

Вспомогательные пакеты:

- `core` — база данных, конфигурация, DI, утилиты приложения

## Слоистость модулей

Каждый модуль придерживается единой плоской структуры:

```text
module/
  models.py       SQLAlchemy ORM-модели, таблицы
  repository.py   запросы к БД, работа с сессией
  router.py       FastAPI-маршруты, зависимости, HTTP-схемы
  schemas.py      Pydantic-схемы и внутренние DTO
  service/
    *.py          пользовательские сценарии, транзакционные границы
```

Вложенные продуктовые подмодули не используются. Различия сценариев выражаются именами файлов в `service/`.

## Правила межмодульных зависимостей

```text
HTTP (router.py) -> service/*.py -> repository.py -> models.py
                        |
                        +-> другие модули (только через их service/*.py)
                        +-> ai facade (app.modules.ai.facade)
```

- Модуль обращается к другому модулю только через публичные функции его `service/*.py`.
- Прямой доступ к чужим `repository.py` и `models.py` запрещён.
- `router.py` остаётся тонким: принять запрос, вызвать сервис, вернуть схему ответа.
- AI-клиенты вызываются через централизованный `app.modules.ai.facade`.

## Модель запросов и транзакций

Синхронные HTTP-запросы используют зависимости FastAPI для создания сессии БД на запрос.

Важное правило:

- внешние AI-вызовы по возможности выполняются до открытия write-транзакции
- транзакции в БД должны быть короткими и заниматься только сохранением данных

Это особенно важно для генерации `context_definition` в `vocabulary` и проверки ответов с помощью AI в `training`.

## Persistence и база данных

PostgreSQL — основное хранилище. SQLAlchemy-модели определены внутри каждого модуля. Миграции Alembic лежат в `alembic/versions/` (13 версий).

Ключевые принципы:

- данные пользователя изолированы на уровне каждой таблицы через `user_id`
- `dictionary_entries` — общий словарь, переиспользуется всеми пользователями
- `user_vocabulary` — личный словарь, ссылается на `dictionary_entries`
- SRS-состояние хранится в `word_progress`, статусы вычисляются в коде

SQLite используется только в тестах (in-memory), архитектура ориентирована на PostgreSQL.

## Политика использования AI

AI используется только там, где нужна семантика, генерация или пояснения.

Текущая гибридная стратегия:

- перевод: сначала `dictionary_entries` → базовый лексикон → локальные эвристики → удалённый AI
- `context_definition`: сначала переиспользуется готовое определение, AI — только при отсутствии кандидата
- генерация упражнений: AI для свободной генерации, локальный fallback при недоступности
- проверка ответов: детерминированная логика, AI — только для семантической проверки

Это снижает latency, стоимость и зависимость от доступности внешнего провайдера.

## Фоновые задачи

Celery выполняет тяжёлые операции: создание словарных элементов с AI, генерация упражнений.

Ключевые свойства:

- эндпоинты, запускающие задачи, возвращают `202 Accepted` с `task_id`
- статус задачи доступен через `GET /api/v1/tasks/{task_id}`
- каждая задача привязана к `owner_user_id`; только владелец может опрашивать статус

## Модуль graph

`graph` формирует персональный семантический профиль пользователя:

- автоматически выводит интересы из сохранённых слов и контекстов
- хранит конкретные смыслы слов через `WordSense`, чтобы разные значения одной леммы оставались разделёнными
- связывает словарную запись с найденным смыслом через `VocabularySenseLink`
- показывает простые семантические связи: другие смыслы той же леммы или слова из той же темы

Расписание повторений и учёт ошибок остаются в модуле `review`.
`graph` отвечает на вопросы «какая тема интересна пользователю» и «какой смысл слова используется».

## Основные продуктовые потоки

### 1. Перевод и захват

1. Клиент отправляет текст на перевод.
2. Сценарий перевода в `vocabulary` ищет перевод: общий словарь → базовый лексикон → эвристика → AI.
3. Расширение или клиентское приложение может сохранить слово в `user_vocabulary`.

### 2. Сохранение словарного элемента

1. Пользователь отправляет лемму, перевод и контекст (через очередь Celery).
2. Модуль `vocabulary` ищет существующую запись в `dictionary_entries`.
3. Если запись найдена — переиспользуется, AI не вызывается.
4. Если нет — AI строит `context_definition`, создаётся новая запись.
5. Итоговый элемент сохраняется в `user_vocabulary`.

### 3. Генерация и прохождение упражнений

1. `training` готовит упражнения трёх типов в фоне через Celery.
2. Пользователь отправляет ответы через `POST /sessions/submit`.
3. Сначала выполняются детерминированные проверки.
4. Семантическая проверка с AI включается только при необходимости.
5. Обновляется `word_progress` в модуле `review`.

### 4. Повторение

1. Модуль `review` строит очередь из слов с наступившим сроком (`next_review_at ≤ now`).
2. Пользователь проходит повторение, каждый ответ обновляет `word_progress`.
3. SRS-шаги: [1, 3, 7, 14, 30, 60] дней. Правильный ответ продвигает срок, ошибка сбрасывает.
