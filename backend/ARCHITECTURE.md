# Архитектура backend

## Обзор

Backend - это FastAPI-based модульный монолит. Система разделена на бизнес-модули с явными границами. Такой подход позволяет разворачивать проект как одно приложение и удерживать доменную логику в управляемом виде.

Основные runtime-компоненты:

- FastAPI-приложение
- PostgreSQL
- Redis как broker и result backend
- Celery worker для фоновых задач
- Flower для мониторинга задач

Backend является источником истины для:

- аутентификации и user identity
- словарных элементов и их контекстных определений
- контекстного перевода
- генерации и проверки упражнений
- состояния repetition flow и SRS-повторения
- semantic profile пользователя: интересов, смыслов слов и anchors

## Общая структура

Точка входа находится в `app/`. Бизнес-логика организована по четырем укрупненным доменным модулям:

- `identity`
  - `auth`: вход, регистрация, выпуск JWT
  - `users`: профиль пользователя и preferences
- `vocabulary`
  - словарные элементы, контекстные определения, CRUD
  - внутренний flow `from-capture`
  - перевод и локальный базовый словарь как подмодули словарного контура
- `learning`
  - `exercise_engine`: orchestration генерации упражнений
  - `session`: отправка ответов, проверка, scoring, история сессий
  - `review`: SRS-oriented рекомендации на повторение и `word_progress`
- `learning_graph`: semantic profile пользователя, интересы, `WordSense`, anchors
- `core`: база данных, конфигурация, DI, bootstrap приложения

Отдельно от бизнес-модулей существуют технические adapter и infrastructure слои:

- `ai_services`: централизованный adapter к внешнему AI и локальным fallback
- `infrastructure/tasks`: API статуса фоновых задач

## Правила дизайна модулей

Каждый модуль должен быть внутренне цельным и иметь маленькую, осознанную публичную поверхность.

Для крупных модулей, состоящих из нескольких подмодулей, используется единая иерархическая схема:

- корень модуля содержит только `__init__.py`, папку `api/` и подмодули
- `api/router.py` собирает внешние HTTP-роуты модуля
- предметная логика живет внутри подмодулей, а корень крупного модуля остается контейнером

Типичная структура подмодуля:

- `models.py`: SQLAlchemy-модели подмодуля
- `repository.py`: persistence и query logic
- `application_service.py`: orchestration и бизнес-use-case
- `contracts.py`: внутренние DTO для обмена между слоями и модулями
- `assembler.py`: преобразование ORM-объектов, contracts и API-схем
- `router.py`: FastAPI-endpoints подмодуля
- `public_api.py`: явно экспортируемые функции для других модулей

Эта схема не является обязательной для маленьких частей системы. Если подмодуль содержит простую логику без отдельной БД-таблицы или публичного межмодульного API, он может состоять из меньшего числа файлов.

Правила границ:

- межмодульный доступ к данным проходит через стабильные публичные контракты
- межмодульный доступ должен идти через `public_api.py` или согласованные contracts
- router должен оставаться тонким и делегировать работу application service
- AI-клиенты вызываются через централизованный `ai_services`

Оптимальная слоистость для проекта:

- `router.py`: HTTP, авторизация текущего пользователя, валидация query/body
- `application_service.py`: пользовательский сценарий и транзакционные границы
- `repository.py`: чтение и запись данных
- `models.py`: ORM-модель и ограничения таблицы
- `contracts.py`: DTO для public API и межмодульного обмена
- `schemas.py`: Pydantic-схемы внешнего HTTP API
- `public_api.py`: маленький фасад для других модулей
- `assembler.py`: преобразования между model, DTO и schemas, когда они не помещаются в одну-две строки

## Модель запросов и транзакций

Синхронные HTTP-запросы используют FastAPI dependencies для создания DB session на запрос. Orchestration записи принадлежит application service.

В backend действует важное operational-правило:

- внешние AI-вызовы по возможности должны происходить до открытия write-транзакции
- транзакции в БД должны быть короткими и заниматься только persistence

Это особенно важно для:

- генерации `context_definition` в `vocabulary`
- AI-assisted проверки ответов в `learning/session`

Цель - закрывать транзакции БД до ожидания сетевого ответа от AI-провайдера.

## Persistence и база данных

PostgreSQL - основное production-хранилище. SQLAlchemy-модели определены внутри модулей, миграции Alembic лежат в `alembic/versions/`.

Текущие принципы хранения:

- изоляция пользовательских данных является базовым требованием для словаря, review-потоков и задач
- review scheduling и tracking прогресса находятся рядом с learning flow
- graph-related структуры сохраняются в базе и используются как semantic profile пользователя

SQLite по-прежнему используется в части легковесного test setup, но production-архитектура ориентирована на поведение PostgreSQL.

## Политика использования AI

Backend использует AI как слой усиления для задач, где важна семантика, генерация или поясняющий feedback.

Текущее поведение:

- перевод работает по модели hybrid-first: glossary, локальные mappings и heuristics запускаются раньше удаленного AI
- `context_definition` обязательно для словарных элементов, но система сначала пытается reuse и только потом вызывает LLM
- генерация упражнений использует AI только там, где действительно нужна свободная генерация или семантическая гибкость
- проверка ответов эскалирует к AI только тогда, когда детерминированной логики недостаточно

Это снижает latency, стоимость и operational risk, сохраняя ценность AI там, где действительно важна семантика.

## Фоновые задачи и task layer

Celery используется для асинхронных операций, например генерации упражнений и других потенциально дорогих workflows. Redis выступает broker'ом и result backend.

В проекте также есть local fallback task registry для dev-oriented сценариев. Статус задач отдается через инфраструктурный слой `infrastructure/tasks`.

Ключевые ограничения:

- ownership задач привязан к пользователю
- endpoint статуса задачи отдает metadata только владельцу задачи
- записи local fallback считаются временными и очищаются по TTL

## Learning graph

`learning_graph` формирует персональный semantic profile пользователя. Его ответственность:

- автоматически выводить интересы пользователя из сохраненных слов и контекстов
- хранить конкретные смыслы слов через `WordSense`, чтобы разные значения одной леммы оставались разделенными
- связывать словарную запись с найденным смыслом
- показывать легкие semantic anchors: другие смыслы той же леммы или слова из той же темы

Ошибки пользователя и расписание повторений остаются в `learning/session` и `learning/review`.
Так границы проще защищать:

- `learning/review` решает, когда повторять
- `learning/session` фиксирует ответы и ошибки
- `learning_graph` объясняет, какой смысл слова используется и какие темы интересны пользователю
- `exercise_engine` может использовать эти сигналы при подготовке упражнений

Рекомендации на повторение строятся в первую очередь по SRS, due words и recent mistakes.
Interest profile из `learning_graph` дополняет SRS контекстом интересов и смысла слова.

## Основные продуктовые потоки

### 1. Перевод и захват

1. Клиент отправляет текст на перевод.
2. Подмодуль `vocabulary/translation` выбирает лучший доступный перевод через локальную логику и AI fallback.
3. Расширение или frontend может сохранить слово или фразу в словарь.

### 2. Сохранение словарного элемента

1. Пользователь отправляет лемму, перевод и исходный контекст.
2. Модуль `vocabulary` пытается переиспользовать уже существующее контекстное определение.
3. Если confidence недостаточный, AI строит новое определение.
4. Финальный словарный элемент сохраняется вместе с definition metadata.

### 3. Генерация и прохождение упражнений

1. `learning/exercise_engine` готовит упражнения синхронно или в фоне.
2. `learning/session` принимает ответы.
3. Сначала выполняются детерминированные проверки.
4. AI-assisted semantic evaluation включается только при необходимости.
5. Обновляется прогресс обучения и review state.

### 4. Повторение

1. `learning/review` строит review plan на основе due words и recent mistakes.
2. Frontend показывает кандидатов на повторение и запускает тренировочный поток.
3. `learning_graph` отдельно дает слова из профиля интересов и semantic anchors для объяснения связей.

## Архитектурный фокус

Backend реализован как модульный монолит, оптимизированный под один учебный цикл: захватить слово, понять его в контексте, потренировать и повторить в нужный момент.

Ключевые инженерные акценты:

- единое FastAPI-приложение с явными границами модулей
- SRS-oriented повторение уже сохраненной лексики
- semantic profile пользователя через `learning_graph`
- асинхронные задачи для долгих AI-операций
