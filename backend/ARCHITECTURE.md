# Архитектура серверной части

## Обзор

Серверная часть представляет собой модульный монолит на FastAPI. Система разделена на бизнес-модули с явными границами. Такой подход позволяет разворачивать проект как одно приложение и удерживать доменную логику в управляемом виде.

Основные компоненты среды выполнения:

- FastAPI-приложение
- PostgreSQL
- Redis как брокер сообщений и хранилище результатов
- рабочий процесс Celery для фоновых задач
- Flower для мониторинга задач

Серверная часть является источником истины для:

- аутентификации и пользовательской учетной записи
- словарных элементов и их контекстных определений
- контекстного перевода
- генерации и проверки упражнений
- состояния сценария повторения и SRS-повторения
- семантического профиля пользователя: интересов, смыслов слов и смысловых связей

## Общая структура

Точка входа находится в `app/`. Бизнес-логика организована по верхнеуровневым модулям:

- `identity`
  - вход, регистрация, выпуск JWT
  - профиль пользователя и preferences
- `vocabulary`
  - словарные элементы, контекстные определения, CRUD
  - сценарий `from-capture`
  - перевод и локальный базовый словарь
- `learning`
  - координация генерации упражнений
  - отправка ответов, проверка, оценивание, история сессий
  - SRS-повторение и `word_progress`
- `learning_graph`: семантический профиль пользователя, интересы, `WordSense`, смысловые связи
- `core`: база данных, конфигурация, DI, bootstrap приложения

Отдельно от бизнес-модулей существуют технические слои адаптеров и инфраструктуры:

- `ai_services`: централизованный адаптер к внешнему AI и локальным резервным сценариям
- `platform/tasks`: API статуса фоновых задач

## Правила дизайна модулей

Каждый модуль должен быть внутренне цельным и иметь маленькую, осознанную публичную поверхность.

Все продуктовые модули используют одинаковую слоистую схему:

- `api`: HTTP-маршруты, зависимости, Pydantic-схемы запросов и ответов
- `application`: пользовательские сценарии и транзакционные границы
- `domain`: SQLAlchemy-модели, DTO/контракты и assemblers
- `adapters`: репозитории, запросы к БД и технические адаптеры
- `public_api.py` или `*_public_api.py`: явно экспортируемые фасады для других модулей

Вложенные продуктовые подмодули не используются. Если внутри модуля есть несколько сценариев, они разделяются именами файлов в слоях ниже API: например `exercise_service.py`, `session_schemas.py`, `review_models.py`. HTTP-маршруты модуля живут в едином `api/router.py`.

Правила границ:

- межмодульный доступ к данным проходит через стабильные публичные контракты
- межмодульный доступ должен идти через публичный фасад или согласованные контракты
- router должен оставаться тонким и делегировать работу application-слою
- AI-клиенты вызываются через централизованный `ai_services`

Оптимальная слоистость для проекта:

- `api/router.py`: HTTP, авторизация текущего пользователя, проверка параметров запроса и тела запроса
- `api/*_schemas.py`: Pydantic-схемы внешнего HTTP API
- `application/*_service.py`: пользовательский сценарий и транзакционные границы
- `adapters/*_repository.py`: чтение и запись данных
- `domain/*_models.py`: ORM-модель и ограничения таблицы
- `domain/*_contracts.py`: DTO для public API и межмодульного обмена
- `domain/*_assembler.py`: преобразования между ORM-моделью, DTO и схемами

## Модель запросов и транзакций

Синхронные HTTP-запросы используют зависимости FastAPI для создания сессии БД на запрос. Координация записи принадлежит application service.

В серверной части действует важное эксплуатационное правило:

- внешние AI-вызовы по возможности должны происходить до открытия write-транзакции
- транзакции в БД должны быть короткими и заниматься только сохранением данных

Это особенно важно для:

- генерации `context_definition` в `vocabulary`
- проверки ответов с помощью AI в сценарии учебных сессий

Цель - закрывать транзакции БД до ожидания сетевого ответа от AI-провайдера.

## Persistence и база данных

PostgreSQL является основным хранилищем для развернутой версии. SQLAlchemy-модели определены внутри модулей, миграции Alembic лежат в `alembic/versions/`.

Текущие принципы хранения:

- изоляция пользовательских данных является базовым требованием для словаря, потоков повторения и задач
- расписание повторений и отслеживание прогресса находятся рядом со сценарием обучения
- структуры learning graph сохраняются в базе и используются как семантический профиль пользователя

SQLite по-прежнему используется в части легковесной тестовой настройки, но архитектура развернутой версии ориентирована на поведение PostgreSQL.

## Политика использования AI

Серверная часть использует AI как слой усиления для задач, где важна семантика, генерация или поясняющая обратная связь.

Текущее поведение:

- перевод работает по гибридной модели: глоссарий, локальные соответствия и эвристики запускаются раньше удаленного AI
- `context_definition` обязательно для словарных элементов, но система сначала пытается переиспользовать готовое определение и только потом вызывает LLM
- генерация упражнений использует AI только там, где действительно нужна свободная генерация или семантическая гибкость
- проверка ответов обращается к AI только тогда, когда детерминированной логики недостаточно

Это снижает latency, стоимость и operational risk, сохраняя ценность AI там, где действительно важна семантика.

## Фоновые задачи и инфраструктурный слой задач

Celery используется для асинхронных операций, например генерации упражнений и других потенциально дорогих сценариев. Redis выступает брокером сообщений и хранилищем результатов.

В проекте также есть локальный резервный реестр задач для сценариев разработки. Статус задач отдается через технический слой `platform/tasks`.

Ключевые ограничения:

- ownership задач привязан к пользователю
- маршрут статуса задачи отдает метаданные только владельцу задачи
- записи локального резервного режима считаются временными и очищаются по TTL

## Learning graph

`learning_graph` формирует персональный семантический профиль пользователя. Его ответственность:

- автоматически выводить интересы пользователя из сохраненных слов и контекстов
- хранить конкретные смыслы слов через `WordSense`, чтобы разные значения одной леммы оставались разделенными
- связывать словарную запись с найденным смыслом
- показывать простые смысловые связи: другие смыслы той же леммы или слова из той же темы

Ошибки пользователя и расписание повторений остаются в модуле `learning`.
Так границы проще защищать:

- сценарий review решает, когда повторять
- сценарий session фиксирует ответы и ошибки
- `learning_graph` объясняет, какой смысл слова используется и какие темы интересны пользователю
- `exercise_engine` может использовать эти сигналы при подготовке упражнений

Рекомендации на повторение строятся в первую очередь по SRS, словам с наступившим сроком повторения и недавним ошибкам.
Профиль интересов из `learning_graph` дополняет SRS контекстом интересов и смысла слова.

## Основные продуктовые потоки

### 1. Перевод и захват

1. Клиент отправляет текст на перевод.
2. Сценарий перевода в `vocabulary` выбирает лучший доступный перевод через локальную логику и резервное обращение к AI.
3. Расширение или клиентское приложение может сохранить слово или фразу в словарь.

### 2. Сохранение словарного элемента

1. Пользователь отправляет лемму, перевод и исходный контекст.
2. Модуль `vocabulary` пытается переиспользовать уже существующее контекстное определение.
3. Если confidence недостаточный, AI строит новое определение.
4. Итоговый словарный элемент сохраняется вместе с метаданными определения.

### 3. Генерация и прохождение упражнений

1. Сценарий exercise engine в `learning` готовит упражнения синхронно или в фоне.
2. Сценарий session в `learning` принимает ответы.
3. Сначала выполняются детерминированные проверки.
4. Семантическая проверка с AI включается только при необходимости.
5. Обновляется прогресс обучения и состояние повторения.

### 4. Повторение

1. Сценарий review в `learning` строит план повторения на основе слов, срок повторения которых наступил, и недавних ошибок.
2. Клиентское приложение показывает кандидатов на повторение и запускает тренировочный поток.
3. `learning_graph` отдельно дает слова из профиля интересов и смысловые связи для объяснения связей.

## Архитектурный фокус

Серверная часть реализована как модульный монолит, оптимизированный под один учебный цикл: захватить слово, понять его в контексте, потренировать и повторить в нужный момент.

Ключевые инженерные акценты:

- единое FastAPI-приложение с явными границами модулей
- SRS-oriented повторение уже сохраненной лексики
- семантический профиль пользователя через `learning_graph`
- асинхронные задачи для долгих AI-операций
