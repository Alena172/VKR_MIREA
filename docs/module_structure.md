# Структура модулей серверной части

## Цель

Серверная часть устроена как модульный монолит: проект запускается как одно FastAPI-приложение, но бизнес-логика разделена на самостоятельные модули.

Оптимальная структура модуля должна помогать читать код и защищать архитектуру. Слои добавляются там, где они отделяют разные ответственности. Для маленькой логики лишние файлы не создаются.

## Модули верхнего уровня

### `identity`

Отвечает за пользователя и авторизацию:

- регистрация и вход
- выпуск и проверка JWT
- профиль пользователя

### `vocabulary`

Отвечает за личный словарь:

- сохранение слов и контекстов
- перевод
- сценарий `from-capture`
- базовый локальный лексикон

### `learning`

Отвечает за учебный цикл:

- генерация упражнений
- прохождение сессий
- сохранение ответов
- SRS и план повторения

### `learning_graph`

Отвечает за семантический профиль пользователя:

- автоматическое определение интересов
- разные смыслы одной леммы через `WordSense`
- связь словаря с конкретным смыслом
- смысловые связи
- слова из профиля интересов

### `ai_services`

Это слой адаптера, а не отдельный продуктовый домен. Он скрывает работу с внешним AI-провайдером, локальными резервными сценариями и генерацией текста.

### `infrastructure`

Содержит технические механизмы, которые обслуживают приложение:

- API статуса задач
- интеграция с Celery/Redis

## Базовая слоистость

Для полноценного доменного подмодуля используется такая структура:

```text
module_or_submodule/
  router.py
  schemas.py
  application_service.py
  repository.py
  models.py
  contracts.py
  assembler.py
  public_api.py
```

Для каждого модуля верхнего уровня используется единая HTTP-точка входа:

```text
module/
  api/
    router.py
```

`api/router.py` собирает или переэкспортирует router модуля. Благодаря этому `core/api.py` подключает все модули верхнего уровня одинаково.

Назначение слоев:

- `router.py` принимает HTTP-запрос, получает текущего пользователя и вызывает application service.
- `schemas.py` описывает внешние Pydantic-схемы HTTP API.
- `application_service.py` реализует пользовательский сценарий и управляет транзакционными границами.
- `repository.py` содержит запросы к базе данных.
- `models.py` содержит SQLAlchemy-модели и ограничения таблиц.
- `contracts.py` содержит DTO для межмодульного обмена.
- `assembler.py` преобразует ORM-модели в DTO и API-ответы.
- `public_api.py` содержит маленький фасад, через который другие модули вызывают этот модуль.

## Когда слой можно не создавать

Слой можно не выделять, если он не дает самостоятельной пользы.

Практические правила:

- `models.py` нужен только там, где модуль владеет таблицами.
- `repository.py` нужен, когда есть нетривиальная работа с БД.
- `public_api.py` нужен, когда модуль вызывается другими модулями.
- `contracts.py` нужен, когда данные выходят за границы модуля.
- `assembler.py` нужен, когда преобразования повторяются или становятся шумными.
- `application_service.py` нужен для пользовательских сценариев; простые методы адаптера могут жить в service-классе.

## Правило межмодульных зависимостей

Модуль может обращаться к другому модулю через:

- `public_api.py`
- DTO из `contracts.py`
- согласованный адаптер или фасад

Модуль не обращается напрямую к чужим:

- `repository.py`
- `models.py`
- `application_service.py`

Так сохраняется понятная граница: один модуль может менять внутреннюю реализацию, не ломая остальные.

## Рекомендуемая структура по текущим модулям

### `identity`

Оставить текущую структуру:

```text
identity/
  api/
  auth/
  users/
```

`auth` и `users` достаточно самостоятельны, поэтому их разделение оправдано.

### `vocabulary`

Оставить как крупный модуль с подмодулями:

```text
vocabulary/
  api/
  items/
  translation/
  base_lexicon/
  flows/
```

`flows` объясняется как слой пользовательских сценариев, который координирует словарь, AI-адаптер, SRS и семантический профиль через public API.

### `learning`

Оставить как один доменный модуль с тремя подмодулями:

```text
learning/
  api/
  exercise_engine/
  session/
  review/
```

Разделение соответствует продуктовому циклу: создать упражнение, принять ответ, обновить повторение.

### `learning_graph`

Оставить компактным модулем без дополнительных подмодулей:

```text
learning_graph/
  api/
  router.py
  schemas.py
  application_service.py
  repository.py
  models.py
  contracts.py
  assembler.py
  public_api.py
```

Дополнительные подпапки для `interests`, `word_senses` или `relations` сейчас добавят сложности. Для дипломной модели достаточно объяснять `learning_graph` как единый семантический профиль.

### `ai_services`

Оставить плоским слоем адаптера:

```text
ai_services/
  api/
  router.py
  service.py
  chat_client.py
  translation_service.py
  exercise_generator.py
  definition_resolver.py
  contracts.py
```

Здесь не нужна полноценная доменная слоистость с `repository.py` и `models.py`, потому что слой не владеет бизнес-сущностями в БД.

## Итоговое правило

Проект придерживается умеренной слоистости:

```text
HTTP API -> application service -> repository/model
             |
             +-> public API других модулей
             +-> адаптер внешних сервисов
```

Эта структура сохраняет преимущества модульного монолита: единый запуск, простая эксплуатация и понятные границы ответственности.
